# 字段与访谈完成标准

## 案例主题

每个案例分别维护下列主题。项目清单建好后，尚未深访的案例也保留这些主题，状态为 `unasked`。回答已足够时收束；不要求每位受访者回答问题库的每一道题。

| 状态键 | 对应问题 | 足够具体的内容 |
| --- | --- | --- |
| identity | I、C01–02 | 可区分的客户/产品、任务、时间范围、提供方与项目归属；真实实践与参考/规划分开 |
| problem | C03–07、D02 | 原始需求、实际痛点、受影响角色、需求澄清或取舍的实例；标品说明其目标问题和实际反馈 |
| workflow | W | 一条任务的输入、原流程、新流程、输出与保留的人工环节 |
| solution | S、P01–05 | 已有交付物、各自用途、已实现/规划边界与选择原因；主动采集已有截图、文档和录屏 |
| contribution | R、D03 | 本人及其他人的角色、亲自完成的关键产物或决策，至少一个具体经历及其结果/局限 |
| engineering | E、D04 | 与本人角色相关的数据/系统依赖、难点、验证和失败处理；非技术角色记录参与的验证与协作边界 |
| stage | T01、T03–06 | 截至日期、真实使用范围、交付/验收/采购/付款的独立状态与未完成部分 |
| duration | T02、T07 | 首版、完整交付、运行和本人投入的可得时间，区分所指范围 |
| commercial | B、D01 | 合作与签约关系、获客方式、金额与口径、回款；内部项目说明无外部合同与可知投入 |
| outcomes | V | 至少具体结果或反馈；有数字需带基线/范围/时间/来源/人工参与/目标或测算属性；无统计明确说明 |
| reuse | U、S06、D05 | 可复用部分、下一客户的前提、定制与权利限制、适用和不适用条件 |
| materials | M | 按 [材料采集](materials.md) 建立实际文件清单，记录项目/版本、支持的说法、取得状态与不能提供的原因 |
| publication | L01–03 | 正文与不同附件各自可用用途、实名/金额/画面等脱敏要求；未授权内容只在本地保留 |
| current_offer | A、P06–07 | 当前可售范围、报价/计费、交付和售前边界、渠道结算与对接方式；未约定事项如实保留 |

materials 标为 answered 时，另按 [材料采集](materials.md) 提供 material_collection。文字中的材料清单不能代替实际收件记录；只有待提供时仍保持开放。

共同合作信息只问一次，各案例以来源引用并写出适用差异；不能因为共享信息就省掉另一个案例的事实核对。某个子问题不适用时记录原因，不必让整组问题都变成未知。深度以具体任务、责任、判断与依据为准，字段非空不代表足够。

## 已有案例库字段映射

以下对应 2026-10-29 核对的 26 个字段。操作真实表格前读取当时字段与选项；这些说明用于采集和输出，并不授权写库。

| 案例库字段 | 访谈主题/来源 | 记录要求 |
| --- | --- | --- |
| 案例名称 | identity、I04 | 具体客户任务；匿名标识可用，系列不假装成单一客户 |
| 案例提供方 | identity、contribution | 个人/公司/团队及归属，区分多人发言 |
| 行业 | identity、C01 | 与场景分开，写库时匹配实际选项 |
| 客户画像 | identity、C01–02 | 客户类型、规模、使用者与决策者；实名按权限 |
| 业务场景 | problem、C/W | 用业务任务分类，写库时匹配实际选项 |
| 问题与原有流程 | problem、workflow | 谁原来怎么做、痛点、需求目标与澄清 |
| 方案与交付物 | solution、workflow | 输入—处理—输出—人工—交付物；嵌入关键取舍 |
| 数据与系统依赖 | engineering | 数据可得性、接口、部署、权限、硬件与关键工具 |
| FDE参与及交付分工 | contribution | 本人、雇主、伙伴与客户分别负责什么 |
| 交付阶段 | stage | 规划/演示Demo/PoC验证/试点或试用/已交付上线/暂停或终止/不明确，按实际选项写入并保留依据 |
| 商务阶段 | stage、commercial | 未签约/预算或采购中/已签约未回款/部分回款/已结清/内部项目/不明确；与交付独立 |
| 交付周期 | duration | 首版、完整交付、持续运行、本人投入分开 |
| 合作方式 | commercial | 历史合作关系，可有总包/分包/咨询等复合形式 |
| 金额及口径 | commercial | 币种、预算/报价/合同/实收/年费、主体、费用构成与含税情况；不强转单个数 |
| 成效及口径 | outcomes | 每条分别标本人陈述/测算/目标、统计范围与依据，说明人工作用和限制 |
| 复用条件与限制 | reuse | 下一客户前提、定制、权利、失败原因与边界 |
| 可用资料 | materials | 已收到/仅展示/可提供/无资料，分别列明，不混用 |
| 公开范围与脱敏要求 | publication | 文字、客户实名、金额、画面、代码、合同、视频分别说明用途和限制 |
| 待补问问题 | 问题与冲突记录 | 只保留具体问题、核验人/材料；已明确未知的事实要写原因，避免永久重复追问 |
| 整理状态 | 整理工作进度 | 现有选项为已整理完成/待整理，表示内容提取进度；证据不足写说明，不发明状态 |
| 来源访谈 | 实际来源记录 | 关联对应访谈；没有已有记录时不伪造飞书关联 |
| 访谈定位 | source_refs | 沿用逐字稿时间戳或本次轮次，未经检查不能说已核准到视频 |
| 原始录音/视频 | 来源访谈关联公式 | 由系统关联，不手工伪造链接 |
| 案例编号 | 系统 | 自动编号，不询问受访者 |
| 自动处理标识 | 系统 | 写库流程使用的稳定去重标识，不询问受访者 |
| 最近更新时间 | 系统 | 系统更新时间，不拿文件修改时间推断项目/访谈日期 |

当前可售方案、参考报价与计费方式、渠道分润与结算、合作对接人属于合作补充信息，尚不能假定案例库已有同名字段。先保存在本地案例补充；真实字段支持后再映射，不能直接向不存在字段写入。

## 官网案例卡映射

以官网运行时 `solution-schema --json` 为准。当前方案字段映射如下：

| 官网字段 | 访谈内容 |
| --- | --- |
| title / industry | 案例名称 / 行业 |
| stage | 调研与方案设计 research、工程原型 prototype、局部试点 pilot、实际运行 operating；无适合值时保留空值及正文阶段说明，不能把暂停误记为运行 |
| scenario | 客户画像与业务任务 |
| problem | 问题与原流程 |
| approach | 方案、交付物、新流程与关键依赖 |
| contribution | 个人贡献、团队分工和关键决策 |
| outcomes | 结果、验证范围、证据、测算属性及局限 |
| content | 不重复主卡的补充：时间、商务阶段、金额口径、复用、现售方案、合作条件、来源及仍未知事项；只放获准上传内容 |

详细状态可作为经确认的结构化附件，避免为迁就九个字段丢掉关键事实。私有读入的合同、对话全文和未经授权的来源路径不随正文自动发送。认证申请与案例提交是两个操作。

## 会话记录与覆盖检查

维护如下结构；可以增加来源索引、附件、当前报价等内容。`source_refs` 引用会话内可定位的文件/页码/时间戳/回答，不用含密钥或完整私有原文。

```json
{
  "round": 1,
  "status": "active",
  "sources": [{"id": "reply:1", "type": "provider_statement", "locator": "第1轮回答"}],
  "questions": [
    {"id": "q1", "bank_ids": ["V01", "V08"], "case_id": "case-1", "topic": "outcomes", "question": "上线后有哪些变化，有没有统计？", "status": "answered", "answer": "没有统计，也没留反馈记录。", "source_refs": ["reply:1"]}
  ],
  "cases": [{
    "id": "case-1", "title": "匿名项目",
    "topics": {
      "identity": {"status": "answered", "summary": "对应的具体客户任务与归属", "source_refs": ["reply:1"]},
      "outcomes": {"status": "unknown", "reason": "本人明确没有统计或反馈记录", "question_ids": ["q1"]}
    },
    "conflicts": []
  }]
}
```

主题状态：

- `unasked`：未问或未从材料获得；`partial`：已有信息但不够具体。两者继续追问。
- `answered`：满足上表的实质标准，有 `summary` 和 `source_refs`。来源可以是本人陈述，但来源类型不能冒充独立核验。
- `unknown` / `declined`：已经问过且本人明确不知道/不愿披露，带 `reason` 与已回答的 `question_ids`。不能把“材料未提及”直接标成此状态。
- `not_applicable`：带适用性原因；涉及真实实践不存在、权限或商务敏感时优先如实标注，不用不适用掩盖没问。

问题记录使用 `pending`、`answered`、`withdrawn`；撤回需说明合并、重复等原因，不用撤回躲开缺口。保留实际回答，不仅记录“已问”。同一回答涉及多案例时为各案例保留对应问题或来源引用。

冲突记录包含 `id`、`topic`、至少两个 `claims`（每条有 `text` 和 `source_refs`）及状态。`open` 继续问；`resolved` 写 `resolution`、`source_refs`；已追问但本人不能确认或拒绝确认，可记 `unknown`/`declined`，附 `reason` 和 `question_ids`，保留人工核验。旧说法始终留档。

运行：`python3 <本Skill目录>/scripts/interview_status.py <session.json>`。脚本输出未覆盖主题、待答问题、未消解冲突和人工核验项；结构错误退出 2，需要继续访谈退出 1，覆盖记录可供用户确认退出 0。

即使报告 `ready_for_user_confirmation: true`，也只表示采集记录已覆盖或明确留有边界，不证明事实真实、案例完整、认证通过或允许上传。AI 仍须按实质标准检查答案；权限不明的内容不上传。用户暂停时 `status: paused`，保存进度；明确提前结束时 `status: ended`，保留未完成记录并交付部分成果。
