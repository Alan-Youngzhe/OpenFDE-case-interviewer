# 材料采集

每个案例在讲清一条实际业务流程后，主动请本人提供能展示实际成果的已有材料。围绕该案例举出合适的选择：产品或系统截图、输入输出对比、交付文档/PPT 节选、操作录屏。请本人直接发送，或授权一个明确目录后查找。已有文件优先，不要求为采集重做材料。

拿到文件后核对对应项目、版本、真实/模拟数据、支持的说法、敏感信息和可用范围。系统画面中的客户信息可先脱敏；原件不能离开本机时，询问是否有可分享的节选或已有演示链接。确实没有、不便提供或拒绝时，记录本人回答与原因，保留文字案例并明确证据限制。配图和 AI 生成的示意图不能冒充真实系统截图或交付证据。

## 实际材料清单

每个案例在 session.json 中维护 `material_collection`，不要用“可提供截图”代替实际收件：

```json
{
  "status": "received",
  "source_refs": ["reply:3"],
  "assets": [{
    "id": "asset-1",
    "name": "流程结果.png",
    "kind": "screenshot",
    "local_path": "./materials/result.png",
    "size": 48320,
    "supports": "展示差异清单与人工复核界面",
    "source_refs": ["reply:3"]
  }]
}
```

- `pending`：尚未实际收件，带具体 `next_action`，继续跟进；本人暂停时保存待补项。
- `received`：已取得实际文件，`assets` 非空；逐项记录文件名、真实本地路径、字节数、种类、支持内容及来源。检查文件存在且可读取后再记为已收到。
- `link_only`：只有已有演示链接，`links` 非空，带 `reason` 说明没有可上传文件；不计作附件上传。
- `unavailable` / `declined`：本人明确没有或不能提供，带 `reason` 和本案例 materials 主题已回答的 `question_ids`。

所有状态提供 `source_refs`。收到部分材料仍有承诺未交的部分时，用 `pending` 保留已收 `assets` 和剩余动作，避免把承诺计成完成。材料主题的 summary 写具体内容与限制，完成标准同时核对本清单。

## 上传与提交核验

本人确认本批正文、实际文件与用途后，按 [官网接入](website.md) 上传。每个实际附件使用独立稳定请求编号。附件写入返回 `fileId` 后，把它与已确认的文件名、实际字节数写进私有 `attachment-manifest.json`：

```json
{
  "solution_id": "官网案例 UUID",
  "files": [{"file_id": "上传回执 fileId", "name": "流程结果.png", "size": 48320}]
}
```

清单覆盖本批所有获准上传文件；尚未取得 fileId 的条目保留为空，核验会报错，不能删除条目来掩盖遗漏。只有本人明确无可提供附件时，使用空 `files` 并填写 `no_attachments_reason`，最终注明“仅文字”。本地清单、原始路径与会话记录留在私有工作区。

先通过官方 CLI 导出服务器记录，运行 `scripts/verify_submission.py` 核对草稿附件。本人同意正式提交后，再导出新记录并加 `--submitted` 核对提交快照。仅草稿上传成功不等于评审已收到；未核验成功时保留官网案例 ID、请求编号和部分回执，先查记录、沿用原请求编号恢复，避免重复创建。
